    inductive PropertyKindCalculus.KindEdges.EdgeLaw :
    Type

    The law a witness family states — the shape of its kind equation. Every reader of specs keys on it (the dimensional rule, the graph roles, the interchange family), so each is a total match that a family added to the registry cannot silently fall out of.

    • product : EdgeLaw

      k₁ · k₂ → k.

    • quotient : EdgeLaw

      k₁ / k₂ → k.

    • reciprocal : EdgeLaw

      1 / k₁ → k₂.

    • transcendental : EdgeLaw

      transcendental : k₁ → k₂.

    • power : EdgeLaw

      k₁ ^ p → k₂, the exponent p a rational, not a kind.

    • reference : EdgeLaw

      reference : k₁ → k₂: a re-expression relates the value converted; the two reference quantities are the edge's configuration, not further operands.

    • additive : EdgeLaw

      k ± k → k: the witness names one kind, which is both operands and the result.

                      partial def PropertyKindCalculus.KindEdges.collectInlineEdges (env : Lean.Environment) (e : Lean.Expr) (acc : Array (EdgeSpec × Array Lean.Expr)) :
                      Array (EdgeSpec × Array Lean.Expr)

                      Collect every inline edge of an expression — the body complement of collectEdges' type scan. A constant-headed application whose instantiated conclusion is a witness-family Prop is an edge at its use site, whatever spelling the elaborator chose: the direct smart-constructor application (ProductKind.ofRatio k₁ k₂ k …), the reference to a lifted ._proof_N auxiliary, the reference to a shared auxiliary (the elaborator dedups alpha-equivalent nested proofs of several definitions into one auxiliary — the later definitions' values then hold nothing but this reference, and the type scan alone would attribute their edges to the first definition), and the reference to a named witness theorem. A free-variable-headed witness is deliberately not collected: that is a hypothesis — assumed, not authored. Returns the same shape as collectEdges, arguments in the family formatter's order.

                      def PropertyKindCalculus.KindEdges.producerModules (env : Lean.Environment) :
                      Std.HashSet Nat

                      The module indices whose import closure contains the module defining the witness families — the only modules whose declarations can possibly reference them. Both scans skip every other module's constants: a type, like a body, can only mention a family whose defining module its own module transitively imports, so the walk scales with the calculus's own downstream, not with the environment (type-scanning every constant of an import Lean environment alone costs a default command's whole heartbeat budget, and walking every value costs hundreds of millions of allocation heartbeats). Constants of the module currently elaborating have no module index and are always scanned. The header's module arrays are in load order (an import precedes its importer), which is what makes the single forward pass a fixpoint.

                        def PropertyKindCalculus.KindEdges.bodyScannable (reachable : Std.HashSet Nat) (env : Lean.Environment) (name : Lean.Name) (info : Lean.ConstantInfo) :
                        Lean.MetaM Bool

                        Is this constant one the body scan should read? Definitions only: a producer inside a theorem's proof term proves the theorem's stated type, which the type scan already lists — the body scan is for computations that consume a witness inline. Instances are skipped for the same reason: an instance's value builds its registration, and the registration — the instance's type — is the authored edge, owned by the type scan (else every [table] row would repeat as a naked edge read off the value). Compiler-generated machinery (recOn/casesOn, ._flat_ctor, matchers) is skipped: the witness structures' own plumbing applies their constructors without authoring anything, and a matcher's branches live in its caller's value, not the matcher's. reachable is producerModules env, computed once per walk.

                                The harvest #

                                Every edge enumeration is a renderer over one environment walk, harvest: #kind_edges below (through edgesMentioning), the kind index's Algebra column (edgesByKind), the dimensional gate (DimensionalCoverage.coverageRows), and the kind digraph #kind_scc and #kind_footprint read (Graph.KindGraph.kindGraphOf). The split exists for the same reason BoundaryAudit.boundarySites exists: the enumeration is wanted both as the info message an author reads and as table rows a document renders. Because a kind's authored edges are the statement of what may be done with it algebraically, this is the column that makes a rendered kind index worth reading — see PropertyKindCalculus.Index. Sharing the walk is what makes the reports agree on what an authored edge is: collectEdges and collectInlineEdges are called from here alone.

                                  def PropertyKindCalculus.KindEdges.harvest {α : Type} (keep : Lean.Name → Bool) (render : EdgeSpec → Array Lean.Expr → Lean.MetaM (Option α)) :
                                  Lean.MetaM (Array (Lean.Name × α))

                                  The one edge-harvest walk. For every constant of a family-reaching module (producerModules) whose authoring declaration (parentOf) passes keep, both channels are scanned and each (family, arguments) pair found is handed to render, which runs inside the telescope that binds the pair's variables (so a parametric kind prints as its binder name) and returns none to drop the pair:

                                  • the type scan reads the declaration's conclusion only (forallTelescopeReducing, then collectEdges): a named witness theorem, a lifted ._proof_N auxiliary, an operator-table instance. A witness taken as a hypothesis ((h : ProductKind …) → …) is assumed, not authored, and is deliberately not an edge — the same line the body scan draws for a free-variable-headed witness;
                                  • the body scan reads the value of every bodyScannable definition under its own telescope (collectInlineEdges): the call-site witnesses the elaborator left inline or shared.

                                  The result is in walk order, the type channel before the body channel of each constant, undeduplicated: each renderer owns its own dedup key (per author, per equation, per kind).

                                              Grouping a kind's edges for a rendered cell #

                                              edgesByKind deduplicates by (author, edge) — the right identity for the per-author report, and the wrong one for a rendered cell, which drops the author and would show one copy of a · b → c per authoring declaration. The renderers therefore share one grouping: deduplicate by the equation alone, then split by the side the kind stands on — the edges producing it (it is the right-hand side) from the edges consuming it (it enters as an operand).

                                                def PropertyKindCalculus.KindEdges.groupEdges (short : String) (edges : Array KindEdge) :
                                                Array (String × Array (String × Lean.Name))

                                                The edges mentioning the kind displayed as short, deduplicated by equation and grouped for rendering: the produced group (the kind is the result) and the consumed group (the kind is an operand), each labeled with its count, empty groups omitted. Each equation carries one authoring declaration — the alphabetically first, when several authored the same equation — so a rendered cell can link the equation to a declaration that authored it. The consumed group sorts by result first, so edges yielding a common kind sit together; an edge with the kind on both sides counts as produced.

                                                  def PropertyKindCalculus.KindEdges.edgesByKind (targets : Array Lean.Name) :
                                                  Lean.MetaM (Std.HashMap Lean.Name (Array KindEdge))

                                                  The edges mentioning each of targets, in one environment walk.

                                                  The single-target edgesMentioning is the right shape for #kind_edges, which asks about one kind. It is the wrong shape for an index over a hundred kinds: that would walk the environment a hundred times. A rendered kind table wants this one instead. An edge mentioning two kinds is listed under both, which is what makes the column readable from either end.

                                                  Kinds are rendered by their last name component here, where #kind_edges prints them fully qualified. That is not an inconsistency to fix: #kind_edges is read in a file whose namespace is open, where the qualified name disambiguates, while a table cell holding four edges of qualified names is a paragraph of repeated prefixes with the content buried in it. The table is scoped to a namespace already, so the short name is unambiguous there.
